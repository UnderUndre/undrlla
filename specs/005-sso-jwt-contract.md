## 1. Intent & Core Principle

Define the single canonical authentication & session delegation contract across the Undrlla ecosystem.

> ### 🛑 Zero-Code Auth Law (No Custom Auth Wheels)
> We **DO NOT** write custom auth, JWT generators, or password hashers from scratch.
> 1. **Flagship IdP (`id.undrlla.network`)**: Uses **native Directus 12.x Authentication** out of the box (`/auth/login`, `/auth/refresh`, OIDC/OAuth2 providers, JWKS signing).
> 2. **Client Stores (`undreseller`)**: Uses **native Medusa 2.0 Auth Module (`@medusajs/auth`)** for store customers.
> 3. **Federation**: Ecosystem services validate Directus-issued RS256 JWTs via standard OAuth2/OIDC JWKS endpoints.

## 3. JWT Schema Specifications

All ecosystem tokens MUST be signed using **RS256** (RSA-SHA256) via Directus native key management. Asymmetric keys allow any ecosystem service to verify tokens locally using the public JWKS endpoint without hitting the IdP on every request.

### 3.1 Public JWKS Endpoint
- **URL**: `https://id.undrlla.network/.well-known/jwks.json`
- **Key Rotation**: Dual-key rotation scheme with `kid` (Key ID) header in JWTs.

### 3.2 Canonical User Access Token Payload

```json
{
  "iss": "https://id.undrlla.network",
  "sub": "usr_01H9Y78Z9A1B2C3D4E5F6G7H8J",
  "aud": ["undrlla-ecosystem", "undreseller", "undrllanding"],
  "exp": 1785200000,
  "iat": 1785196400,
  "jti": "jwt_01H9Y78Z...",
  "username": "undre_dev",
  "email": "dev@undrlla.network",
  "status": "citizen",
  "roles": ["undrlla.citizen", "tenant.customer"],
  "tenant_id": "tnt_default_flagship",
  "capabilities": ["shop:read", "shop:cart", "unet:tunnel"]
}
```

## 4. Session Delegation & Cookie Domains

### 4.1 Ecosystem Wildcard Subdomains (`*.undrlla.network`)
- **Cookie Name**: `__Secure-undrlla-session`
- **Domain**: `.undrlla.network`
- **Attributes**: `SameSite=Lax; Secure; HttpOnly; Path=/`
- **Usage**: Automatically passed across all official ecosystem subdomains (`id.undrlla.network`, `app.undrlla.network`, `shop.undrlla.network`).

### 4.2 Custom Client Domains (e.g. `myshop.com`)
For client-owned custom domains deployed via `undevops`:
1. Customer logs in on `myshop.com`.
2. App redirects to `https://id.undrlla.network/oauth/authorize` (Directus OIDC PKCE flow).
3. User authenticates → redirects back to `myshop.com/api/auth/callback?code=...`.
4. Storefront exchanges authorization code for local Medusa session token & stores HTTP-only cookie on `myshop.com`.

## 5. Medusa 2.0 Integration Contract

Client shops (`undreseller`) accept both:
1. Native Medusa customer session tokens (`medusa_session` generated by `@medusajs/auth`).
2. Federated Undrlla JWTs (`Authorization: Bearer <token>`).

Medusa integration plugin `undrlla-auth-module` verifies the RS256 JWT via Directus JWKS, extracts `sub`, `email`, and `username`, and auto-provisions or links the corresponding Medusa `Customer` entity in Postgres.

---

## 6. Security Requirements (OpSec)

- **FR-SSO-01**: Access tokens MUST NOT have an expiration (`exp`) longer than **1 hour**.
- **FR-SSO-02**: Refresh tokens MUST be opaque, stored in `HttpOnly` cookies, and subject to automatic rotation with reuse detection via Directus session store.
- **FR-SSO-03**: No service in the ecosystem MAY store plaintext passwords; authentication is centralized exclusively in native Directus IdP.
- **FR-SSO-04**: CORS headers MUST explicitly list authorized origin domains; wildcards (`Access-Control-Allow-Origin: *`) with credentials are strictly forbidden.
